# 08 GPU-hour 成本核算

## 诊断问题

任务从调度到终止实际占用了多少 GPU 资源，失败和重算是否计入总成本？

## 输入参数

| 参数 | 含义 |
|---|---|
| Pod `start_at` | 资源开始驻留时间 |
| Pod `stop_at` | 资源停止驻留时间 |
| GPU count | 该 Pod 占用卡数 |
| task status | 成功、失败、取消 |
| duplicate run records | 重复提交或重跑 |

## 操作步骤

1. 使用终态 Pod 字段，不混用运行态临时字段。
2. 对每个 Pod 计算 `(stop_at - start_at) × GPU count / 3600`。
3. 多 Pod 任务对所有 Pod 求和。
4. 成功、失败、准备、重算和重复任务分别记录，再汇总完整项目成本。
5. `start_at=null` 时报告成本未知，不填零。
6. 运行中的任务不计入“终态实际成本”，可另列上界。

## 输出结果

32 卡扩展全部终态任务合计 54.7611 H20·h。成功任务中：

- train-05：12.5311 H20·h；
- publication-01：19.4844 H20·h。

四卡 Ray-ready 任务为 1.453333 H20·h；冷恢复保留任务为 2.053333 H20·h。

## 最终诊断结论

项目成本必须包含失败任务、准备、诊断和重算，不能只报告成功训练 step。Pod GPU-hour 是资源驻留口径，不是 GPU kernel 活跃时间，也不是平台账单。

## 原理说明

资源分配期间，即使进程在等待、加载模型或做 CPU hash，GPU 仍被任务占用。按 Pod 驻留核算能反映实验占用的资源机会成本；利用率和计费需要其他证据。

## 注意事项

- timeline `start_run` 与 Pod `start_at` 不是同一字段。
- 主动取消且没有 start time 的任务不能按 0 成本处理。
- 并发任务的 GPU-hour 可以相加，墙钟不能相加。
- 保守预留、实际驻留和平台账单应分开。
